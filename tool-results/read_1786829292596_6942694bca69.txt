    20→    20→============================================================
    21→    21→                    CORE PRINCIPLES
    22→    22→============================================================
    23→    23→
    24→    24→1. DO NOT REWRITE THE ENTIRE APPLICATION.
    25→    25→2. KEEP working functionality unless there is a documented architectural reason to replace it.
    26→    26→3. FIX existing functionality before adding duplicate functionality.
    27→    27→4. SECURITY HAS PRIORITY OVER NEW FEATURES.
    28→    28→5. MULTI-TENANT ISOLATION IS NON-NEGOTIABLE.
    29→    29→6. NEVER TRUST CLIENT-SUPPLIED organizationId, userId, role, permissions or resource ownership.
    30→    30→7. SERVER-SIDE AUTHORIZATION IS REQUIRED FOR EVERY PROTECTED OPERATION.
    31→    31→8. NEVER expose secrets, API keys, tokens or webhook secrets.
    32→    32→9. NEVER use production database-destructive commands.
    33→    33→10. NEVER use `db push --accept-data-loss` as a production migration strategy.
    34→    34→11. NEVER use localStorage for sensitive authentication tokens if a secure HttpOnly session architecture can be used.
    35→    35→12. NEVER hard-code AI answers that should come from live system data.
    36→    36→13. Mianx.ai must operate through authorized tools and real RTR360 data.
    37→    37→14. Every major change must be tested.
    38→    38→15. Existing APIs must remain backward compatible unless intentionally versioned.
    39→    39→16. Every destructive or breaking change requires explicit documentation.
    40→    40→17. Every feature must have acceptance criteria.
    41→    41→18. No fake/mock production functionality may be presented as real functionality.
    42→    42→19. No "TODO" implementation may be considered complete.
    43→    43→20. Never mark a phase complete if its acceptance tests fail.
