============================================================
                    CORE PRINCIPLES
============================================================

1. DO NOT REWRITE THE ENTIRE APPLICATION.
2. KEEP working functionality unless there is a documented architectural reason to replace it.
3. FIX existing functionality before adding duplicate functionality.
4. SECURITY HAS PRIORITY OVER NEW FEATURES.
5. MULTI-TENANT ISOLATION IS NON-NEGOTIABLE.
6. NEVER TRUST CLIENT-SUPPLIED organizationId, userId, role, permissions or resource ownership.
7. SERVER-SIDE AUTHORIZATION IS REQUIRED FOR EVERY PROTECTED OPERATION.
8. NEVER expose secrets, API keys, tokens or webhook secrets.
9. NEVER use production database-destructive commands.
10. NEVER use `db push --accept-data-loss` as a production migration strategy.
11. NEVER use localStorage for sensitive authentication tokens if a secure HttpOnly session architecture can be used.
12. NEVER hard-code AI answers that should come from live system data.
13. Mianx.ai must operate through authorized tools and real RTR360 data.
14. Every major change must be tested.
15. Existing APIs must remain backward compatible unless intentionally versioned.
16. Every destructive or breaking change requires explicit documentation.
17. Every feature must have acceptance criteria.
18. No fake/mock production functionality may be presented as real functionality.
19. No "TODO" implementation may be considered complete.
20. Never mark a phase complete if its acceptance tests fail.

------------------------------------------------------------
MULTI-TENANT ISOLATION
------------------------------------------------------------

Every tenant-scoped resource MUST belong to exactly one organization.

Every protected request must establish:

authenticatedUser
+
authenticatedUser.organizationId
+
requestedResource.organizationId

These must be validated server-side.

Rule:

IF authenticated user has no valid organization context
THEN deny access.

Never:

- trust organizationId from request body
- trust organizationId from query parameters
- trust organizationId from frontend
- trust user-provided ownership claims

Every database query must be appropriately tenant-scoped.

Test for:

- cross-tenant GET
- cross-tenant POST
- cross-tenant PUT
- cross-tenant PATCH
- cross-tenant DELETE
- cross-tenant nested resources
- cross-tenant bulk operations
- cross-tenant exports
- cross-tenant reports
- cross-tenant AI access

Expected result:

CROSS-TENANT ACCESS = 403 OR NOT FOUND

Never leak existence of another tenant's data.
